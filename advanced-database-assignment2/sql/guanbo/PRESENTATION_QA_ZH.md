## 第一部分：5 分钟演讲怎么讲

不要从头念代码。按"**问题 → 设计 → 证据**"三段讲，每段都有落点。

### 第 1 段（40 秒）我负责什么

> 我负责 Member 5：KYC/AML 的异常发现与上报。上游给我两类事件——客户做过什么 KYC 验证、被名单库筛查过几次。我要做的是：**用规则判断哪些事件构成合规问题，把问题变成可跟进的案件，最后算成监管报表**。

### 第 2 段（2 分钟）核心设计（这是加分点）

讲这三个决定，它们能体现你懂业务而不只是会写 SQL：

**① 事件表和案件表为什么要分开**

> 验证和筛查是**事件**，来一条记一条，永不覆盖。问题是**案件**，同一个问题只保留一个。如果混在一张表里，同一个客户反复出现同一个毛病，就会开出一堆重复案件，报表上的"异常笔数"就没有意义了。
>
> 所以我做了**复用逻辑**：同一个验证事件加同一种问题类型，只生成一个案件。代码里 `find_or_open_verification_case` 就是干这个的——先查有没有，有就返回旧的，没有才建。

**② 筛查命中不等于洗钱，所以案件只做"复核"**

> 名单命中只是"疑似"。所以我的 AML 案件类型固定是 `AML_SCREENING_REVIEW`（警报复核），而不是"确认违规"。这也是为什么我把消息表和处理表分开——不让疑似变成定性结论。

**③ 异常账龄要能累积**

> 报表要回答"这笔异常挂了多久"。所以异常事实表是**累积型**的：案件没结时，每次刷新**更新同一行**，而不是新增行。而且账龄按报告基准日封顶——不能出现"挂了 41 天"但报告期只有 30 天这种自相矛盾的数字。

### 第 3 段（1 分钟）证据

> 我不是只写完就交了。我用一个**真实的 PostgreSQL 引擎把这些脚本真正跑了一遍**（PGlite，编译成 WebAssembly 的 PostgreSQL），并且写了断言：注错一条数据、少一条注释，测试就会失败。
>
> 这个过程抓出了 7 个静态检查看不出来的真实缺陷，其中一个是：共享建表里 `fact_compliance_exception` 的两个唯一索引，因为 PostgreSQL 把 NULL 视为互不相同，会导致**事实表只能插入 1 行**，第 2 行就报错。这个问题只有真正执行才会暴露。

> **准备好这句话**：这是在展示工程严谨性，比"我写了 9 个文件"有说服力得多。

## 第二部分：高频问题与标准答案

### A. 关于数据模型

**Q1：为什么事件表和案件表要分成两张？**
A：事件是流水（一行一次行为），案件是待办事项（一行一个问题）。分开才能既保留完整历史，又让"问题"不重复计数。见 `kyc_verification_record` vs `special_verification_case`。

**Q2：`customer_id` 为什么允许为空？**
A：因为身份合并（Member 2）可能还没完成。作业明确要求"身份未解决的事件也要能保留并上报"，所以我允许它为空，同时要求至少有一个来源客户记录做主体（这是 `ck_kyc_verification_record_subject` 这条 CHECK 约束在保证的）。

**Q3：如果 `customer_id` 和 `source_customer_record_id` 都填了，但指向不同的人怎么办？**
A：这正是我要抓的异常之一，规则 `KYC_IDENTITY_LINK_MISMATCH`，会开 `IDENTITY_MISMATCH` 案件。

**Q4：为什么要用 MD5 生成主键？不能自增吗？**
A：因为要**可重复执行**。同一批数据跑两次，自增会生成两个不同的编号，就重复插入了。用"来源系统 + 来源编号" 算 MD5，跑多少次都是同一个编号，天然幂等。

**Q5：`expiry_date`（有效期）到底怎么用？**
A：判断一次 KYC 验证**还能不能复用**。拿它跟报告基准日比：晚于基准日才算仍然有效。作业要求"减少重复 KYC 检查，但不能把旧的验证无限期当有效"，就是靠这一列。

### B. 关于规则与案件

**Q6：一共多少条规则？怎么分类？**
A：**18 条**检测规则，分两组：**KYC 验证事件 8 条**、**AML 筛查事件 10 条**，分别实现在两个检测函数里。
另外还有 **7 条「案件状态规则」**（比如「已解决必须有解决时间」），它们不是检测函数，而是用数据库 CHECK 约束实现的——这样任何代码路径都无法写入非法状态。
（如果被追问细节，翻 `README.md` 的规则表：KYC 与 AML 分开列，每行含规则名、发现内容、对应案件类型、严重程度。）

**Q7：阻断（BLOCKING）和可报告（REPORTABLE）有什么区别？**
A：阻断级问题会让**这条事件根本不进入 Silver 层**（比如连主体都没有，无法归属）；其余问题照常进 Silver，同时登记数据质量问题，并按规则决定是否开案件。

**Q8：什么情况会开案件？**
A：只有**映射到案件类型的规则**才开案件。作业明确要求"可报告的 KYC 缺口、身份不匹配、状态矛盾必须建 KYC_GAP / IDENTITY_MISMATCH / STATUS_DISCREPANCY 案件"。映射关系集中在 `compliance_rule_case_type` 这一个函数里——这是刻意的，**单一事实来源**，改口径只改一处。

**Q9：那"身份尚未合并"这种提示为什么不建案件？**
A：它是 LOW 级别的**提示**，不是合规异常。身份还在处理中不等于违规。所以我把它保留成数据质量问题（报表能看到），但不建案件。如果这里建了案件，案件数会虚高，监管口径就错了。

**Q10：同一个问题反复出现会怎样？**
A：**复用已有案件**，不会新增。案件编号由"事件 + 案件类型"生成，代码先查后建。我专门写了测试断言这一点（`v_cases_after = v_cases_before`）。

### C. 关于报表与事实表

**Q11：为什么叫"累积快照事实表"？**
A：因为它的行会随案件进展被**更新**而不是追加。未结案时每次刷新算一次账龄；结案后记录结案日。这样能回答"这笔异常开了多久"。

**Q12：`verification_case_id` 和 `aml_case_id` 为什么必须只有一个？**
A：因为一笔异常只能来自一个来源。两个都填说明数据错了，两个都空说明没有来源。有 CHECK 约束 `ck_fact_compliance_exception_single_case` 强制这一点。

**Q13：`days_open` 怎么算？**
A：= 结案日（未结案时用报告基准日）− 开案日，且**用 LEAST 按基准日封顶**。我特意加了断言"账龄不能超过报告期"。

**Q14：`customer_key` 为空的行是不是被丢掉了？**
A：**没有**。报表用左连接保留它们，显示为身份未确认。作业要求"未解决身份的案件也要出现在报表里"。

**Q15：最高严重程度怎么取的？**
A：用**显式的等级排序**（紧急 > 高 > 中 > 低），不是 `max(severity)`。因为按字母排序会得出"MEDIUM 比 HIGH 严重"这种荒谬结果——这是我修过的一个真实缺陷。

### D. 关于工程与协作

**Q16：怎么保证重复执行不会产生重复数据？**
A：三层保证：主键由业务键派生（幂等）、插入用 `ON CONFLICT DO NOTHING/UPDATE`、程序入口先清理临时表。所有脚本都测过重复执行。

**Q17：你怎么验证代码是对的？**
A：两条线。**静态**：用 PostgreSQL 官方解析器（pglast）解析全部 10 个文件。**动态**：用 PGlite（真实 PostgreSQL 编译版）把共享建表、我的模块、数据管道、验收测试全跑一遍，并断言行数和注释。
（如果被问"能不能现场跑"，说：`verification/member5-kyc-aml/` 下 `pnpm install` 后 `node verify.mjs`。）

**Q18：为什么不写存储过程而用函数？**
A：分工不同。**函数**返回结果（如规则检测返回发现列表），**过程**做副作用（如装载、建案）。能用函数就用函数，因为它可以被 SELECT 组合、便于测试。

**Q19：你的模块依赖别人的表吗？**
A：依赖但**不破坏**。我只读 Bronze；对 Member 2 的客户身份表，只在本模块事件引用的身份**尚不存在**时补建，绝不改写已解析好的身份。这一点我在 README 里明确写了。

**Q20：这批数据里到底抓出了什么异常？**
A：三条，都有具体的人和原因：

| 异常 | 客户 | 原因 |
|---|---|---|
| KYC_GAP | Noah Chen | 缺证件（`MISSING_DOCUMENT`） |
| STATUS_DISCREPANCY | Leo Martin | 验证已过有效期（2026-08-15 到期） |
| AML_SCREENING_REVIEW | Olivia Brooks | 监控名单疑似命中，相似度 0.92 |

结果：7 个客户 KYC 状态为"已验证"，2 个为"需复核"。

## 第三部分：被问到不会的怎么办（最重要的一节）

**不要编。** 编造一个字段含义或规则逻辑，一旦被追问细节就会连环崩。用这个三步法：

1. **承认边界**："这部分我没有深入验证，我不想凭印象回答。"
2. **给出你知道的相邻事实**："我能确定的是，这条规则的实现在 `04_create_kyc_aml_validation.sql` 里，它属于 KYC 验证事件这一组。"
3. **承诺可查**："我可以现场打开这个文件确认，或者会后给你准确答案。"

**可以现场演示的"救命动作"**（提前练熟，比嘴上解释更有力）：

```sql
-- 1) 看规则到案件类型的映射（口径问题都靠它回答）
SELECT silver.compliance_rule_case_type('KYC_VERIFICATION_INCOMPLETE');  -- 返回 KYC_GAP

-- 2) 看某条表/字段的中文说明
SELECT col_description('silver.kyc_verification_record'::regclass, 9);   -- 返回字段 9 的说明

-- 3) 看异常报表长什么样
SELECT * FROM gold.vw_kyc_aml_exception_report;
```

**三种最可能被追问的方向，提前准备好**：

| 追问方向 | 准备什么 |
|---|---|
| "这条规则的阈值/取值依据是什么" | 说清是**业务约定**（作业给定），不是你拍的。比如 `0.75` 是"警报级相似度"的分界，取自报告口径 |
| "如果数据里出现 X 情况会怎样" | 说"我没有造这个场景的数据，但从规则看它会走到 Y 分支"，**不要断言一定如此** |
| "为什么不做成实时/流式" | 作业明确是**批处理原型**，README 里也写了这是刻意选择，不做实时 |
