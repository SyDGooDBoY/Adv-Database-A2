## 二、逐项说明改了什么

### 1. `01`：同一批控制数据原来写了两遍（−102 行）

**原来**：`source_systems.ingestion_batch` 和 `silver.ingestion_batch` 两张表字段相同、数据同源，但各写了一段 VALUES 插入，两段内容完全重复。

**现在**：用一段循环把同一份批次数据同时写入两张表：

```sql
FOREACH v_batch SLICE 1 IN ARRAY v_batches
LOOP
  INSERT INTO source_systems.ingestion_batch (...) VALUES (...);
  INSERT INTO silver.ingestion_batch          (...) VALUES (...);
END LOOP;
```

**为什么安全**：两张表本来就是同一份数据的两个副本，字段为 `varchar`，用文本数组传入再强制转换，等价于原来的字面量插入。

### 2. `03`：KYC 与 AML 两个发布过程近乎逐行重复（−53 行）

**原来**：两个过程各约 190 行，结构完全相同——登记 Bronze 行、查身份、检测问题、发布、留痕、报日志。只有表名和列名不同。

**现在**：抽出两个共用步骤，专用过程只保留各自的 INSERT：

| 新公共对象 | 作用 |
|---|---|
| `silver.stage_bronze_batch(实体, 批次)` | 登记 Bronze 行 + 身份查找（原来重复 2 次，每次 40 行的子查询） |
| `silver.record_event_lineage(实体, 批次)` | 写数据血缘（原来重复 2 段各 55 行） |

**效果**：以后新增第三类合规事件（例如"定期复核"），只需写一个 INSERT，登记与留痕直接复用。

### 3. `04`：两个检测函数各自重复了两段代码（−86 行）

**原来**：KYC 和 AML 两个检测函数里，"身份解析"（约 25 行）和"每条记录只留最严重发现"的排序块（约 15 行）各写了一遍。

**现在**：

| 新公共对象 | 作用 |
|---|---|
| `silver.resolve_event_identity(实体, 来源系统, 来源编号, 批次)` | 一条事件对应哪个来源客户记录／金客户 |
| 排序块口径统一 | 两个函数末尾的 `ranked` 使用完全相同的排序（优先级 → 严重程度 → 规则名） |

**为什么重要**：身份解析口径只有一处，不会出现"KYC 认这个客户、AML 认那个客户"的不一致。

### 4. `09`：注释脚本改用"一条注释四行"的排版（−80 行）

**原来**：每条注释占 4 行（`COMMENT ON` / 对象名 / `IS` / 正文 / `;`）。

**现在**：每条压缩为 2 行（`COMMENT ON 对象 IS` 一行，正文一行），并按"一~九"分节加中文标题。

**注意**：**注释内容一条没删**，仍然是 5 表 + 62 字段 + 3 视图 + 20 个函数/过程全覆盖。

### 5. 全部文件：加中文分节标注

每个文件开头都有"文件结构"清单，正文用 `====` 分节标题隔开，例如：

```
-- 【文件结构】
--   第 1 节  共用步骤：登记 Bronze 行 + 身份查找
--   第 2 节  事件发布：KYC 专用 / AML 专用
--   第 3 节  批次总入口
```

目的是让评审或组员打开文件就能定位，而不必通读全文。

### 6. `05`：两个"查找或建立案件"各写一遍（−29 行）

**原来**：验证案件与 AML 案件的查找/建立流程结构相同——取主体信息、查已有案件、没有就生成编号插入、返回编号——两段各约 115 行。

**现在**：抽出一个通用步骤 `silver.find_or_open_case(实体, ...)`，返回案件编号与触发类型；两个专用函数变成三行的包装：

```sql
SELECT silver.find_or_open_case('KYC', p_case_type, p_kyc_verification_id, ...) ->> 'case_id';
```

**附带好处**："同一问题只开一个案件"这条口径现在只有一处实现，不会出现两类案件规则不一致。

### 7. `06`：事实刷新的两个分支结构相同（删掉 89 行重复，净减 2 行）

**原来**：验证案件与 AML 案件各写一个 `UNION ALL` 分支，每个分支都重复一遍状态映射、客户代理键查找、账龄计算、结案日选择。

**现在**：`UNION ALL` 只负责"把两边的列名与取值统一"，之后的状态映射、代理键查找、账龄封顶只写一遍。

```sql
WITH exception_case AS (
  SELECT 'VERIFICATION' AS source_type, ... FROM silver.special_verification_case
  UNION ALL
  SELECT 'AML', ... FROM silver.aml_case
)
SELECT ... FROM exception_case LEFT JOIN LATERAL (...) dimension ON true;
```

**为什么净减只有 2 行**：删掉的是 89 行重复代码，但合并后的写法补了一段说明"为什么合并、账龄怎么封顶"。**用重复代码换来了可读性**，这正是本次的目标。

## 三、怎么证明功能没变

这是最关键的一节。**同一个验证脚本在重构前后跑出完全相同的业务结果**：

```
$ cd verification/member5-kyc-aml && node verify.mjs
```

| 断言项 | 重构前 | 重构后 |
|---|---|---|
| 发布的 KYC 事件数 | 9 | **9** |
| 发布的 AML 事件数 | 10 | **10** |
| 登记的数据质量问题数 | 3 | **3** |
| 验证案件数 | 2 | **2** |
| AML 案件数 | 1 | **1** |
| 异常事实行数 | 3 | **3** |
| `08_validation_tests.sql` 的 15 组断言 | 通过 | **通过** |
| 带中文注释的对象 | 5 表 / 62 列 / 3 视图 / 17 例程 | **5 表 / 62 列 / 3 视图 / 21 例程** |

> 例程数从 17 变成 20，是因为新增了 4 个公共步骤，不是原有对象丢失——验证脚本会逐个检查这 21 个对象是否都有注释。

另外两类检查同时覆盖：

- **静态**：`validate_syntax.py` 用 PostgreSQL 官方解析器（pglast）解析全部 10 个文件，包含一次整体合并解析。
- **动态**：`verify.mjs` 用 PGlite（编译成 WebAssembly 的真实 PostgreSQL）真正执行共享建表、本模块、数据管道与验收测试。

## 四、如果被问到"为什么只减了 9%，而不是更多"

可以这样回答，这是实话：

> 剩下的大头是**逐条列出的业务规则**（18 条规则各自的判断条件、说明文字、严重程度、案件类型）和**逐列的中文注释**（62 列）。这些是"内容"而不是"重复"——删掉它们就等于删掉业务规则或文档，那才是真的改变功能。
>
> 我减少的是重复：同一份批次数据写两遍、两个发布过程近乎复制粘贴、身份解析在两个函数里各写一遍、事实刷新的两个分支结构相同、两个查找案件函数各写一遍。这些改完，同一件事只在一个地方描述。

**还有一个可以主动讲的判断**：`04` 里还有三处判定条件（是否过期、是否矛盾、是否资料缺口）可以用一个函数合并，能再省约 20 行，但会让函数签名变复杂、调用处不再直观。**收益小、可读性变差，所以我没做。** 知道什么时候停手，比一味压行数更重要。

**这是一个可以主动讲的加分点**：能区分「冗余」和「内容」，也能判断「改动成本」与「可读性收益」。

## 五、重构引入的新对象一览（便于答辩时说明）

| 对象 | 类型 | 一句话说明 |
|---|---|---|
| `silver.stage_bronze_batch` | 过程 | 登记一个批次的 Bronze 行并补上身份信息，KYC/AML 共用 |
| `silver.record_event_lineage` | 过程 | 写"Bronze 原始行 → Silver 事件"的血缘记录，KYC/AML 共用 |
| `silver.resolve_event_identity` | 函数 | 一条事件对应哪个来源客户记录／金客户，两个检测函数共用 |
| `silver.find_or_open_case` | 函数 | 查找或建立案件，KYC 与 AML 两个专用函数共用 |

这四个都是**内部共用步骤**，不改变对外行为；发布过程、检测函数、视图、事实表的对外契约与重构前完全一致。
